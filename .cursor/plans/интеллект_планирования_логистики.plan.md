## Контекст

Сейчас «Планирование отгрузки» (`DailyMixerReportModal` + `lib/dailyMixerReport.ts`) — текстовый отчёт по уже назначенным рейсам для копирования в Макс.

Нужно окно **интеллектуальной логистики** на выбранный день (типично завтра / текущий день отгрузки):

- заранее посчитать парк и очередь;
- **одной кнопкой** разложить весь день;
- **и** по мере живой отгрузки **поэтапно** добавлять миксеры/рейсы из того же окна;

Точка входа: дашборд → день → колонка «Миксеры в работе» → «Планирование отгрузки».

| Тема | Решение |
|------|---------|

| Режимы расчёта | **Оба:** (A) «Весь день» одной кнопкой; (B) поэтапная догрузка по мере отгрузки |
| Пометки в ходе дня | Отработавшие **заявки** и **рейсы** видны/помечены прямо в окне интеллекта |
| Приоритет парка | 1) свои (`mixers.type = 'own'`) → 2) чаще участвовали в прошлых отгрузках → 3) объём бочки / прочее |

| Стык рейсов / буфер | **5 мин** (`TRIP_JOIN_BUFFER_MIN`) |
| Обратная дорога | = время туда |

| Сдвиг цели прибытия (вариант B) | до **±60 мин** |
| Варианты при нехватке | **A** жёсткие времена + добор · **B** сдвиги ±60 · **C** текущий парк / хвост |

## Два режима работы (оба в одном окне)

### A. «Весь день» — одна кнопка

Кнопка **«Рассчитать весь день»**:

- берёт все активные заявки дня + доступный парк (или отмеченный логистом);
- строит полный план рейсов/очереди под прибытия;
- показывает warnings;
- даёт скопировать план в Макс.

Это стартовый «скелет» дня. Дальше жизнь правит план через режим B.

### B. «Этап» — догрузка по мере отгрузки

Из того же окна, когда день уже идёт:

1. Логист видит, что отработало / что в работе / что ещё не закрыто.
2. Отмечает миксеров **на следующий этап** (или система предлагает хвост).
3. Жмёт **«Рассчитать этап»** — пересчитывается **только незакрытый хвост**.
4. Уже отработавшие и помеченные «зафиксировано / в Макс» **не перетираются**.
5. Новый блок снова можно скопировать в Макс.

Так закрывается живой процесс с накладками: опоздание, лишний куб, поломка, сдвиг заявки.

## Пометки отработавших заявок и рейсов

В окне интеллектуальной логистики в ходе отгрузки:

| Сущность | Как помечается |
|----------|----------------|
| Рейс | По статусу live (`Разгружен` / `Возврат` и т.п.) и/или ручная метка «отработан» в черновике плана |
| Заявка | Когда объём закрыт / статус заявки завершён / все её рейсы отработаны — строка «✓ отработана», визуально приглушена |
| В работе | Рейсы `Загрузка` / `В пути` / `На объекте` / `Проблема` — отдельный бейдж |
| Ещё в плане | Не начатые позиции плана — активны для пересчёта этапа |

Источник истины для live-статусов — broadcast `order_mixers` / заявки (когда план уже связан с БД или когда на дне уже есть ручные назначения).  
До Фазы 3 часть пометок может жить в черновике плана (`localStorage`) + ручные галочки логиста.

При **«Рассчитать этап»** движок:

- вход: `lockedTrips` / `doneOrderIds` (отработанные и зафиксированные);
- выход: новый хвост **без** перезаписи locked/done.

## Сценарии

### Утро (подготовка)

1. День = завтра → открыть окно.
2. Подсказка парка: «ориентир N миксеров — объёмы …» (свои в приоритете).
3. **«Рассчитать весь день»** → полный план → копировать в Макс.
4. При необходимости подчистить состав парка и пересчитать.

### День отгрузки (живой процесс)

1. Открыть то же окно на **сегодня**.
2. Видны пометки: отработано / в работе / осталось.
3. Добавить миксеры или сдвинуть хвост → **«Рассчитать этап»**.
4. Скопировать только новый блок в Макс.
5. По мере статусов рейсов строки сами уходят в «отработано».

«Зафиксировано» до Фазы 3 = черновик / ушедший в Макс текст + done-метки.  
После Фазы 3 = ещё и строки в `order_mixers`.

## Формулы (контракт)

### Обратный отсчёт загрузки

```
время_загрузки ≈ delivery_time − road_min − load_min
load_min ≈ 15 мин на соске (PLANT_LOAD_SLOT_MIN; 12–18 от объёма)
road_min = из кэша заявки / travel-time (haversine × 1.3, опц. пробки ×1.25–1.35)
```

### Цикл миксера (для следующих рейсов)

```
цикл ≈ load_min + road_min + unload_min + road_min_back
unload_min = 35 (PLANNER_UNLOAD_MIN)
road_min_back = road_min
```

Следующий рейс того же миксера не раньше окончания цикла; стык по одной заявке — следующий прибывает к концу разгрузки предыдущего ± буфер (**5 мин**, `TRIP_JOIN_BUFFER_MIN`).

### Очередь на одной «соске»

Если слоты погрузки пересекаются — сдвигать более поздние / менее приоритетные и писать `warning`.

### Приоритет парка `rankFleetForDay`

```
score = (type === 'own' ? 1_000_000 : 0) + tripCount * 100 + volumeSum
```

- Окно истории: последние **60 дней** (настройка, 30–90).
- Метрика: число завершённых рейсов (`Разгружен` и аналоги), при равенстве — сумма м³.
- Матч: `order_mixers.mixer_name` ↔ `mixers.number`.
- Новые без истории — в конце своей группы (`own` всё равно выше `rented`).

### Фаза 2 — движок `lib/logisticsPlanner.ts`

**Вход:** заявки, парк, road_time, частота рейсов, `mode: 'full_day' | 'stage'`, `lockedTrips`, `doneOrderIds`.

**Выход:** `trips[]`, `warnings[]`, `fleetHint`, текст для Макс (полный или дельта этапа).

Алгоритм:
1. `rankFleetForDay` + fleet hint.
2. Режим `full_day` — все активные незакрытые заявки; `stage` — горизонт (до времени / хвост / выбранные) минус done.
3. Нарезка бочками с приоритетом ранга.
4. Обратный отсчёт от прибытия; стыковка; одна соска; сдвиги + warnings.
5. Merge: `result = lockedTrips ∪ newTrips` (locked не менять).

Статистика частоты рейсов — лёгкий API или выборка из существующих данных.

Live-пометки: подписка на статусы рейсов/заявок дня → авто done в UI.

**Критерий:** полный день и этап детерминированы; этап не затирает done/locked; копирование в Макс работает.

### Фаза 3 — применение в БД (после обкатки)

- **«Применить в заявки»** → batch запись в `order_mixers`:
  - заменяет только рейсы со статусом «Загрузка» без `loading_started_at` (не выехавшие / не начатые на пульте);
  - рейсы «В пути» / «На объекте» / «Разгружен» / … и активная загрузка — **не трогаем**;
  - самовывоз (`pickup`) в `order_mixers` **не пишем**;
  - плановые `done` не перезаписываем.
- **Опция «Только выбранные заявки»**: по умолчанию — все заявки плана с рейсами; чекбоксами можно отметить подмножество и применить только к ним.
- После записи: DB-триггер шлёт broadcast `order_mixers:all` → таймлайн/дашборд обновляется; окно интеллекта читает те же live-статусы для пометок «в работе» / «отработана».
- История заявки: запись о применении плана (+ `new` → `processing`, как при ручном добавлении миксера).

**Критерий:** диспетчер жмёт «Применить» (все или выбранные) → на дашборде появляются/обновляются рейсы без затирания уже выехавших.

### Фаза 5 — live факт оператора в отчёте (план vs факт)

Диспетчер открывает планирование/отчёт на день и видит **реальную картину отгрузки**, а не только расчётный скелет. Источник факта — пульт оператора БСУ + живые рейсы.

**Опора на уже существующее (не строить realtime с нуля):**
- `production_logs` — `start_time` (кнопка «Начать»), `end_time` (кнопка «Загружен» ≈ выпуск с завода);
- `order_mixers` — `loading_started_at`, статусы (`Загрузка` → `В пути` → `На объекте` → `Разгружен`), `on_site_at`, `unloaded_at`;
- broadcast realtime: `order_mixers:all`, `production_logs:all` (`hooks/useRealtimeOrderMixers`, `useRealtimeProductionLogs`);
- дашборд уже держит live `dayMixerTrips` и передаёт в модалку.

**MVP Фазы 5:**
1. В таблице плана / отчёте рядом с плановыми `loadTime` / `arriveTime` — **факт**: старт загрузки, выпуск, статус, дельта (опоздание/опережение в минутах).
2. Матчинг план ↔ факт: заявка + номер миксера (+ порядок рейса); после Фазы 3 — по `order_mixer.id`.
3. Live-обновление без перезагрузки окна (подписка на уже идущий broadcast).
4. Диспетчер **правит отгрузку в реальном времени** из того же контекста: время / статус / объём через существующие `order-mixers/*` API (как на дашборде).
5. «В работе» / «выпущен» / «отработан» — не только по `Разгружен`, а по полной цепочке статусов + лог оператора.
6. Сироты без записи оператора (`no_operator_record`) — явная пометка: факт неполный (статус поставил диспетчер/водитель в обход пульта).

**После MVP (closed-loop):**
- Фактическое опоздание на соске/выпуске → вход в «Рассчитать этап» (locked от факта, хвост дня переезжает). **Сделано** — авто-этап при росте медианы опоздания (≥8 мин, debounce ~14 с, только «сегодня»).
- Опционально колонка/блок факта в тексте «В Макс». **Сделано** — строки `факт: …` под рейсом.
- Полная связка плана с `order_mixers` в БД (усиливается Фазой 3). **Сделано** — `PlannedTrip.orderMixerId`, `links` из apply, sticky-матч 1:1.

**Критерий:** открыл отчёт на сегодня → видишь план vs факт и задержки в live; можешь поправить рейс не уходя на другую страницу; этап умеет опереться на фактические времена выпуска.

**Статус (28.07.2026):** MVP + closed-loop сделаны.

**Зависимости:** MVP можно начать **до** полной Фазы 3 (матч по заявке+миксеру+порядку на уже существующих рейсах дня). Closed-loop и точный 1:1 — лучше после «Применить в заявки».

### Фаза 6 — общий live-план дня для всех участников

Сейчас черновик интеллекта (`logisticsPlan_*`, текст Макс) живёт в **localStorage** одного браузера. Цель фазы: **один общий план дня**, который в реальном времени видят все нужные участники.

**Проблема v1:** диспетчер A посчитал день → диспетчер B / оператор / второй монитор план не видят, пока не скопируют вручную.

**Опора на уже существующее:**
- broadcast (`hooks/useRealtimeBroadcast`) — тот же стек, что `order_mixers:all` / `production_logs:all`;
- роли staff (dispatcher / manager / admin / operator);
- после Фазы 3 план связан с живыми рейсами — Фаза 6 усиливает «все смотрят одну картину».

**Модель данных (ориентир):**
- таблица дня, напр. `daily_logistics_plans` (ключ `delivery_date` / `dateKey`);
- поля: `trips` (JSON плана), `mixer_ids`, `warnings`, `max_text`, `allow_night`, `use_traffic`, `locked`/`done` метки, `updated_at`, `updated_by` (имя/роль);
- опционально: `editing_by` / `editing_at` — «сейчас правит X» (мягкая блокировка).

**MVP Фазы 6:**
1. При «Рассчитать весь день» / «Этап» / правках — **сохранять план в БД** (не только localStorage; localStorage можно оставить офлайн-кэшем).
2. Broadcast `daily_logistics_plan:<date>` (или `:all`) при upsert — все открытые окна интеллекта на этот день подтягивают снимок.
3. **Read-only для зрителей:** второй диспетчер, менеджер, оператор БСУ видят актуальный план/очередь без перезагрузки.
4. Индикатор в шапке: «План общий · обновил Иван в 09:14» (+ пилюли смены из истории/оператора).
5. Кнопка **«Опубликовать план»** (если нужен явный шаг) или авто-публикация после расчёта.

**После MVP:**
- Совместное редактирование с last-write-wins + предупреждение при устаревшей версии (`updated_at` / etag). **Сделано** — `expectedRevision` → 409, баннер «План устарел».
- Роли: кто считает (edit), кто только смотрит (view); оператор — упрощённый вид (соска / ближайшие слоты). **Сделано** — `PlannerOperatorView` + `editing_by_*` heartbeat.
- Кнопка **«Опубликовать»** вместо авто-PUT на каждую правку. **Сделано** (расчёт/этап/сдвиг по-прежнему публикуют сразу).
- Связка с Фазой 3: публикация может предлагать «Применить в заявки» — опционально, не в этом срезе.
- Виджет на дашборде «План дня (live)» — **сделано**.

**Критерий:** два браузера / два сотрудника открыли планирование на один день → после расчёта у одного второй **сразу** видит те же рейсы и замечания без копипаста и без F5.

**Зависимости:** можно стартовать после стабилизации Фазы 2+ (хранение JSON плана). Полная польза с Фазами 3 и 5 (рейсы в БД + факт на том же экране). Realtime-инфраструктуру заново не строим.

**Статус (28.07.2026):** MVP + коллаборация сделаны. Нужно один раз выполнить обновлённый `scripts/daily-logistics-plans-schema.sql` в Supabase (колонки `editing_by_*`).

## Критерий готовности v1

1. **Утро:** «Рассчитать весь день» → полный план → копирование в Макс.  
2. **День:** в том же окне видны отработавшие заявки/рейсы.  
3. **Догрузка:** «Рассчитать этап» добавляет хвост, не ломая done/зафиксированное.  
4. Подсказка парка учитывает **свои → историю отгрузок**.  
5. В БД рейсы из интеллекта ещё не пишутся (до Фазы 3).

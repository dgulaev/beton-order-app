## Цель
Перенести **приложение (сейчас Vercel)** и **базу (сейчас Supabase Cloud)** на свой Mac mini:
Docker + локальный Supabase + Next.js, чтобы завод работал с локали без облачной БД.

## Часть A. База данных → Mac mini (Docker / локальный Supabase)

### Источник полной копии
Ежедневный дамп в репо: `db-backups/backup-YYYY-MM-DD.sql.gz`  
(GitHub Action `.github/workflows/db-backup.yml`, ~05:00 МСК).

В дампе: схема + данные + RLS/`CREATE POLICY` + **ACL (`GRANT`/`REVOKE`)**  
(`pg_dump --no-owner`, без `--no-acl` с 25.07.2026).

Локальный JSON-снимок склада (`backups/warehouse-*.json`, скрипт
`scripts/db-snapshot-warehouse.mjs`) — **не** полная копия БД, только склад/MEKA
для точечного отката. Для переезда использовать SQL-дамп.

### Правильный путь (не голый Postgres)
Приложение ходит в Supabase URL + anon/service_role + Realtime  
(`lib/supabaseClient.ts`, `lib/supabaseAdmin.ts`, `hooks/useRealtimeBroadcast.ts`).

Поэтому на Mac mini поднимать **стек Supabase в Docker**, а не один контейнер Postgres:

```bash
npx supabase start
# получить локальные URL и ключи (anon / service_role)
# восстановить дамп в локальный DB URL
gunzip -c db-backups/backup-YYYY-MM-DD.sql.gz | psql "$LOCAL_DB_URL"
```

В `.env` / `.env.local` на сервере переключить:
- `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_URL` → локальный API
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`

### Нюансы restore
- В дампе есть `public`, `auth`, `storage`, `realtime` и др. На чистый Postgres
  накатывать целиком рискованно; на **локальный Supabase** — штатный сценарий,
  при конфликтах системных схем — восстановить `public` + функции склада,
  Auth/Realtime оставить от стека.
- Роли `anon` / `authenticated` / `service_role` в локальном Supabase уже есть;
  ACL из дампа как раз помогают совпасть с облаком.
- File Storage сейчас ~0 — почти нечего тащить отдельно.
- Mac mini должен быть **всегда онлайн** (или туннель), если к БД ходят
  клиенты/приложение снаружи.

## Часть B. Приложение → локальный сервер (вместо Vercel)

### 1. node-cron вместо Vercel Cron Jobs
- Установить пакет: `npm install node-cron`
- Создать кастомный `server.js` в корне проекта
- Добавить задачу: каждый день в 00:01 МСК (21:01 UTC) вызывать
  `GET /api/cron/dismiss-notifications` с заголовком `Authorization: Bearer CRON_SECRET`
- Убрать секцию `"crons"` из `vercel.json` (или весь файл, если не нужен)

Пример кода для `server.js`:
```javascript
import cron from 'node-cron';
import { createServer } from 'http';
import next from 'next';

const app = next({ dev: false });
const handle = app.getRequestHandler();

app.prepare().then(() => {
  // 00:01 МСК = 21:01 UTC
  cron.schedule('1 21 * * *', async () => {
    await fetch(`http://localhost:${process.env.PORT || 3000}/api/cron/dismiss-notifications`, {
      headers: { Authorization: `Bearer ${process.env.CRON_SECRET}` }
    });
  });

  createServer(handle).listen(process.env.PORT || 3000, () => {
    console.log('Server ready');
  });
});
```

### 2. Переменные окружения
Перенести все `.env` на Mac mini (из Vercel + локальные ключи Supabase):
- `SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL` → **локальный** стек
- `SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_ANON_KEY` (и `NEXT_PUBLIC_*`)
- `CRON_SECRET`
- `DADATA_API_KEY`
- остальные из текущего Vercel Dashboard

### 3. Альтернатива node-cron — системный crontab
```
1 21 * * * curl -s -H "Authorization: Bearer ВАШ_CRON_SECRET" http://localhost:3000/api/cron/dismiss-notifications
```

### 4. Процесс-менеджер
```bash
npm install -g pm2
pm2 start server.js --name concrete-app
pm2 save && pm2 startup
```

### 5. Nginx / обратный прокси
- Nginx: порт 3000 → 80/443
- SSL (Let's Encrypt или локальный сертификат в LAN)
- Доступ завода: VPN / белый IP / Cloudflare Tunnel — по выбору

# Фикс: кнопка «Загружен» — строка остаётся в очереди

Статус: **сделано** — 02.08.2026: probe после таймаута production-log, таймаут 18 с × 3, без ложного отката в очередь.

Дата фиксации решения: 02.08.2026.

## Симптом (как описано)

Оператор жмёт «Загружен» → строка ещё какое-то время остаётся в «Очередь на загрузку».  
При повторном нажатии уходит в «Отгружено сегодня».  
Наблюдалось уже на проде после фиксов #705 / optimistic-hide.

## Диагноз (по коду, без правки)

Файл: [`app/adminCifra/operator/page.tsx`](app/adminCifra/operator/page.tsx) — `completeLoading` / `persistCompletion` / `fetchWithRetry`.

1. По клику сразу: optimistic в «Отгружено» + `optimisticallyRemovedIds` (очередь должна очиститься).
2. Фон: `POST /production-log` (таймаут **8 с**, до 5 попыток) → затем `POST /order-mixers/status` («В пути», таймаут **25 с**, цемент/силос).
3. Если клиент считает `production-log` проваленным (abort/сеть) — **откат**: строка снова в очередь, pending убирается из «Отгружено».
4. На сервере лог при этом часто **уже есть** (дедуп по `order_mixer_id`).
5. Второй клик: ветка `alreadyLogged` / `skipLogInsert` или серверный `deduplicated: true` → дожимает статус → уезжает в «Отгружено».

Итог: гонка UI ↔ ложный фейл `production-log`, не «кнопка не нажимается».

## Решение (делать, когда скажут «правим оператора»)

1. **Не откатывать сразу** при таймауте/`AbortError`/`Failed to fetch` на `production-log`.
2. После сбоя — **probe**: GET/проверка, есть ли уже лог по `order_mixer_id` (или лёгкий endpoint / ответ дедупа).
   - Лог есть → считать шаг 1 успехом, только дожимать статус (`skipLogInsert`).
   - Лога нет → тогда откат optimistic + понятный alert.
3. Смягчить таймаут `production-log` в `fetchWithRetry` для этого вызова (например 15–20 с) или отдельный probe без полного retry-шторма.
4. Не плодить второй INSERT (серверный дедуп уже есть — сохранить).
5. Не трогать цементный путь status без нужды — он уже с `alreadyDoneStatus` и 25 с.

### Не делать в том же PR

- Не рефакторить всю страницу оператора.
- Не менять автоэтап логистики «заодно».

## Связь с интеллектуальной логистикой

Проверено 02.08.2026: **прямой связи нет**.

- Страница оператора **не** подписана на `daily_logistics_plans:all`.
- Слушает: `order_mixers:all`, `production_logs:all` (+ active-mixers fetch).
- Топик плана и soft-lock heartbeat (50 с) грузят вкладку **Планирование**, не оператора.

Косвенно (общий Supabase/Realtime проекта): если у диспетчера открыт план с частым publish/автоэтапом/`Применить` → `notify_order_mixers_reload` + тяжёлые UPSERT плана, это может добавить задержку API оператора. Но симптом «очередь → второй клик» объясняется откатом `production-log`, а не каналом логистики.

### Нагрузка логистики (для справки)

| Источник | Когда | Риск для оператора |
|---|---|---|
| `daily_logistics_plans` broadcast (полный payload) | publish / автоэтап | Только подписчики плана |
| Soft-lock PATCH / thin heartbeat | ~50 с, пока редактируют | Только план (thin) |
| `mixer-trip-stats` limit 20k | mount вкладки плана | API/БД проекта |
| `Применить` → `notify_order_mixers_reload` | редко | Да: оператор делает refetch mixers |
| Автоэтап commitWavePlan | при «Загрузка» над фантомами | Publish плана; WATCHPOINT в LogisticsPlannerTab |

Если тормоза общие по админке — смотреть Supabase latency + шторм role/heartbeat (отдельная тема), не только логистику.
